# V1 验证总结：`piper-plus@0.7.0` 的 Rust wasm 是否适合 TTS-NG 的 Kokoro

**日期**: 2026-10-03
**包**: `piper-plus@0.7.0`（npm，MIT），wasm `piper-plus-wasm` 0.5.0
**wasm**: `dist/rust-wasm/piper_plus_wasm_bg.wasm` = 60,077,874 B（57.29 MiB），sha256 `f94f1407…6ebca0`
**构建特性**: `multilingual = ["ja", "zh", "ko", "es", "fr", "pt", "sv"]`
**对照**: `lib/models/phonemize/`（当前线上链路）+ `@piper-plus/g2p@0.4.2`（V0 参考）
**样本**: 中/日/英各 10 条，共 30 条（与 V0 完全相同）

---

## 判定：**失败（不通过）**

按本次清单的判定标准逐条核对：

| # | 标准 | 结果 | 判定 |
|---|---|---|---|
| 1 | 安装成功，词典内置（零下载） | 安装 ✅；**日语词典内置 ✅**；**中文拼音词典未随包发布 ❌** | ⚠️ **部分** |
| 2 | API 可用，三语言都能正常调用 | 可调用 ✅，但**英语返回原文字符**（本构建不含 `en`），**中文默认返回汉字** | ❌ **不通过** |
| 3 | **中文产出 IPA/拼音**（V0 失败的关键） | **开箱不产出**（透传）；补 2.7 MB 词典并转格式后产出 | ❌ **不通过**（开箱状态） |
| 4 | **日语正常工作**（V0 失败的关键） | **✅ 通过**，零下载，10/10 正确读音，质量高于现有 JS 链 | ✅ **通过** |
| 5 | 英文质量 ≥ 现有 JS 链 | 本 wasm **没有英语 G2P**，10/10 原样返回输入字符 | ❌ **不通过** |
| 6 | Vocab 兼容或需适配 < 5% | 日语丢 31.4%；中文开箱丢 92.3%（v1.0）/ 78.9%（v1.1-zh） | ❌ **不通过** |
| 7 | 性能达标（80% 指标满足） | 名义 5/6 = **83%**；但其中 2 项测的是空操作，去水分后 4/6 = 67% | ⚠️ **部分** |

命中清单「失败」定义的两条：

- **「中文或日语仍然不工作」** —— 日语工作了，**中文开箱不工作**（返回汉字而非音素）。这是 V0 的核心失败点，在 Rust wasm 路径上**开箱状态依然存在**。
- **「Vocab 需适配 > 20%」** —— 中文 92.3% / 78.9%，日语 31.4%，全部远超 20%。

**「部分通过」的范围**：日语。日语这条路是真实、可用、且质量优于现状的（见 §3.2）。但清单对「部分通过」的定义是「某个语言输出格式需要适配层 / Vocab 需适配 5–20%」——本次是**中文完全不可用 + 三语 vocab 适配量全部超标**，不构成部分通过。

## 0. 三个最关键验证点的答案

| 问题 | 答案 |
|---|---|
| **1. 中文是否产出音素（不是汉字）？** | **开箱：否**，返回汉字。上游仓库里那份拼音词典（2.7 MB）没被发布进 npm 包，且**格式与 Rust 解析器不匹配**（带调符号 vs 要求行尾数字）。补上并转换成 TONE3 后才产出正确 IPA——但那是**我们改过的东西**，不是包的能力。 |
| **2. 日语是否不需要外部下载就能工作？** | **是。** NAIST-JDIC 通过 `include_bytes!()` 编进 wasm（上游注释：wasm 96% 是词典数据），实测 Node 进程零 fetch，10/10 正确读音。**这是 V0 失败点里被真正修掉的那个。** |
| **3. 词典是否内置在 57 MB wasm 中？** | **日语是；中文不是。** 57 MB 里约 55 MB 是日语词典，代码只占 ~2 MB。中文拼音词典在包里**完全没有**（`assets/` 目录不存在，jsDelivr 上 404）。 |

## 2. API（❌ 不通过）

详见 `api-exploration.md`。四条要点：

### 2.1 这个 wasm 不返回音素串，只返回音素 ID

`phonemize(text, lang)` 返回 `{ phonemeIds: Int32Array, prosodyFeatures: Int32Array, phonemeCount }`——**ID 是调用方自己传进去的 `phoneme_id_map` 的下标**。想拿到音素串必须自己反解映射。V1 的做法是传一份**穷举 BMP**（63,456 条）的映射，再反向解码，从而拿到真实音素序列。

这对 P6 是**方向性错配**：P6 §0.1 要「可直接进 Kokoro tokenizer 的音素串」，而这个 API 的前提是「音素串 → 你自己模型的 ID」。

### 2.2 ⚠️ 映射里没有的音素被静默替换成 PAD

用只含 `^ $ _ k o n i w a` 的 9 条映射跑 `こんにちは`：

```
穷举映射   ^ _ k _ o _ [ _ N_n _ n _ i _ ch _ i _ w _ a _ $   count=23
9 条映射   ^ _ k _ o _ _ _ n _ i _ _ i _ w _ a _ $            count=20
仅标记     ^ _ _ _ _ _ _ _ _ _ _ _ _ $                        count=13
```

**不报错、不标记，直接变成分隔符。** 后果两面：做适配层时是陷阱（会拿到「看起来正常但少了音素」的结果，没有任何错误信号——与 V0「中文 0.002 ms 空操作」是同一类假绿）；做验收时是量具（把 Kokoro 词表本身当 id map，`PAD 数 - 1` 就是真实音素数，两者之差就是词表会吞掉的音素数）。§4 的丢字率正是这样测出来的。

### 2.3 语言参数是必需的，`detectLanguage` 不可靠

`.d.ts` 注释说该参数「reserved for future forced-language support，实际始终用自动检测」——**这句是错的**。实测：

| 输入 | `detectLanguage` | hint=`ja` | 不传 hint |
|---|---|---|---|
| 経営 / 日本語 / 漢字 / 経験 / 経済 / 計画 / 東京 … | **全部 `zh`** | 正确日文读音 | **汉字透传** |
| けいえい / こんにちは / テスト … | `ja` | 正确 | 汉字透传 |

**只要串里全是汉字，检测器一律答 `zh`。** 30 条日语样本里 3/10 被误判（経営、日本語、漢字）。不传 hint 时纯汉字日文会被送进中文路径 → 缺词典 → **静默返回汉字**。传了 `ja` 就完全正常。

### 2.4 PUA：多字符音素被压成单码位

piper-plus 把 `ch`、`ky`、`N_n`、`tɕ`、`tone3`、`aʊ` 这类多码位 token 映射到 U+E000–E064 的单个 PUA 码位（上游 `docs/spec/pua-contract.toml` 是权威表，99 条）。**Kokoro 两个词表里一个 PUA 都没有**，所以适配层必须先按表还原，才谈得上映射。

## 3. 输出格式对比（❌ 不通过）

原始数据：`piper-plus-comparison.json`（30 条 × 3 链路）。

分类统计（`wasm` 侧）：

| 语言 | 结果 |
|---|---|
| **ja** | 10/10 `ipa-differs`——**真实 G2P**，但与 JS 链逐字符不同 |
| **zh（开箱）** | 10/10 `passthrough`——返回汉字 |
| **zh（补 TONE3 词典）** | 10/10 `ipa-differs`——真实 G2P |
| **en** | 10/10 `passthrough`——返回输入字符 |

### 3.1 中文

| 输入 | 现有 JS 链 | wasm 开箱 | wasm + TONE3 词典 |
|---|---|---|---|
| 你好 | `ni↓xau↓` | `你好` | `ni{tone2}x{aʊ}{tone3}` |
| 今天天气很好 | `ʨi→ntʰjɛ→ntʰjɛ→nʨʰi↘ xə↓n xau↓` | `今天天气很好` | `tɕin{tone1}tʰiɛn{tone1}tʰiɛn{tone1}tɕʰi{tone4}xən{tone2}x{aʊ}{tone3}` |
| 中文测试 | `ꭧʊ→ŋwə↗n ʦʰɤ↘ʂɻ̩↘` | `中文测试` | `tʂuŋ{tone1}uən{tone2}tsʰɤ{tone4}ʂɻ̩{tone4}` |
| 数字123 | `ʂu↘ʦɹ̩↘ i↘pai↓ɚ↘ʂɻ̩↗ sa→n` | `数字123` | `ʂu{tone4}tsɨ{tone4}123` |

补词典后的读音**是对的**（`你好` 的 3+3 变调 → tone2+tone3 正确），IPA 甚至比 JS 链更规范（`tɕ`/`tʂ`/`tsʰ` vs JS 链的 `ʨ`/`ꭧ`/`ʦ`）。但：

- **声调编码完全不同**：wasm 用 PUA token `tone1..tone5`，Kokoro v1.0 用箭头 `↓→↗↘`，v1.1-zh 用数字 `1`–`5`。
- **数字不读**：`数字123` → `123` 原样透传（JS 链读作 `i↓pai↓ɚ↘ʂɻ̩↗ sa→n`）。**TN 这一层 wasm 里没有**——而 P6 §0.2 把 TN/FST 列为迁 Rust 的**首要理由**。
- **拉丁文透传**：`混合text测试` → `…xɤ{tone2}texttsʰɤ{tone4}…`。`setZhEnDispatch(false)` 实测**不改变输出**。

### 3.2 日语（唯一的好消息）

| 输入 | 现有 JS 链 | wasm |
|---|---|---|
| こんにちは | `koɴniʨiha` | `ko[N_nnichiwa` |
| 東京 | （无样本） | `to[okyoo` |
| 経営 | `keiei` | `ke[eee`（= けーえー） |
| 日本語 | `nihoɴɡo` | `ni[hoN_nggo` |
| 漢字 | `kaɴʥi` | `ka[N_uvularji` |
| ありがとう | `ariɡatou` | `a[ri]gatoo` |
| お元気ですか | `oɡeɴkidesuka` | `o[ge]N_ngkidesUka` |

**wasm 的日语读音质量明显高于现有链路**：

- **助词 は 读 wa**（`こんにちは` → `…wa`），JS 链读 `ha`——JS 链是错的。
- **长音处理正确**（`東京` → `too kyoo`，`ありがとう` → `gatoo`）。
- **拨音按后接音变体**（`N_ng` 后接 g、`N_uvular` 词末）。
- **无声化元音**（`U` = 无声化 u，`I` = 无声化 i）。
- **音高标记** `[`（上升）/`]`（下降）——上游 `_SPECIAL_TOKENS` 定义，不是错误字符。

但输出格式与 JS 链**逐字符不同**，且带 PUA + 音高标记，Kokoro 词表没有。P6 §0.4 要求「逐字符等于 JS 输出，或有记录的更优」——日语这一条**可以论证为「更优」**，但需要把这套音素体系映射到 Kokoro 的音素集。

### 3.3 英语

**这个 wasm 构建里根本没有英语。** Cargo 特性列表 `["ja","zh","ko","es","fr","pt","sv"]` 不含 `en`，所以走 `PassthroughPhonemizer`：

```
en "hello"               -> h e l l o
en "The quick brown fox" -> T h e   q u i c k   b r o w n   f o x
```

这是上游的架构分工（英语由 JS 层承担），不是 bug——但意味着**这 57 MB 对英语一点帮助都没有**。英语仍得依赖 V0 判定失败的 `@piper-plus/g2p`（劣于 espeak）或继续用 espeak（GPL 问题不解决）。

## 4. Vocab 兼容性（❌ 不通过）

原始数据：`vocab-check.json`。两套独立测量。

### 4.1 方法一：把词表本身当 `phoneme_id_map`（最可靠）

利用 §2.2 的 PAD 兜底语义：`PAD 数 - 1` = 真实音素数，非 PAD id 数 = 词表覆盖数，差值 = **词表会吞掉的音素数**。

| 语言 | 词表 | 总音素 | 被吞 | 丢字率 |
|---|---|---|---|---|
| **zh（开箱）** | v1.0 | 52 | 48 | **92.31%** |
| **zh（开箱）** | v1.1-zh | 52 | 41 | **78.85%** |
| **zh（+TONE3 词典）** | v1.0 | 135 | 94 | **69.63%** |
| **zh（+TONE3 词典）** | v1.1-zh | 135 | 95 | **70.37%** |
| **ja** | v1.0 | 105 | 33 | **31.43%** |
| **ja** | v1.1-zh | 105 | 33 | **31.43%** |
| en（透传，见注） | 两者 | 86 | 1 | 1.16% |

> **注**：英语那一行**没有意义**。它测的是「输入字符被原样吐回来」时词表认不认那些字母，不是 G2P 输出。唯一缺的 `g` 是因为 Kokoro 词表用 `ɡ`（U+0261）而输入是 ASCII `g`。这个数字**不能**用来给英语打分。

**即使做完所有适配工作（补词典 + 转格式 + 还原 PUA），中文仍有 ~70% 的音素是 Kokoro 词表解析不了的**——因为 piper-plus 的中文音素体系（`tɕ`/`tʂ`/`tsʰ`/`aʊ`/`iɛn`/`ɻ̩`/`tone1..5`）与 Kokoro v1.1-zh 的注音符号体系是**两套不同的东西**，不是缺几个字符。

### 4.2 方法二：字符集差集

| 语言 | 词表 | 原始形式（PUA 形态） | PUA 展开后 |
|---|---|---|---|
| zh（+词典） | v1.0 | 30/45 = **66.7%** | 7/34 = 20.6% |
| zh（+词典） | v1.1-zh | 28/45 = **62.2%** | 4/34 = 11.8% |
| ja | v1.0 | 9/22 = **40.9%** | 6/24 = 25.0% |
| ja | v1.1-zh | 9/22 = **40.9%** | 6/24 = 25.0% |
| en（透传，见注） | 两者 | 1/25 = 4.0% | 1/25 = 4.0% |

日语那 9 个缺失字符是：`U`、`[`、`]`、`g`，加上 5 个 PUA（`U+E006` `ky`、`U+E00E` `ch`、`U+E01A` `N_n`、`U+E01B` `N_ng`、`U+E01C` `N_uvular`）。

**顺带发现一个具体的、和项目已知问题同类的坑**：wasm 的日语路径输出 **ASCII `g`**（`ありがとう` → `a[ri]gatoo`），而 Kokoro 词表只有 `ɡ`（U+0261）。这正是 P6 spec §1.3 记录的「`KANA_TO_IPA` 里写了 ASCII `g`，导致整个ガ行读成ア行」那个 bug 的同一形态——**换到 Rust 侧仍然要处理，不会自动消失**。同理 `U`（无声化 u）不在 Kokoro v1.0 词表里（它有 `A`/`I`/`O` 但没有 `U`）。

**结论**：按清单标准（< 5% 通过 / 5–20% 需适配 / > 20% 不通过），三种语言全部落在**不通过**区间（日语 31.4%，中文 62–92%）。**PUA 展开可以把中文压到 11.8–20.6%（进入「需适配」区间），但日语仍在 25%。**

## 5. 性能（⚠️ 部分通过）

原始数据：`performance-results.json`。50 字符样本，20 次迭代，截尾均值。

| 指标 | 目标 | 实测 | 判定 |
|---|---|---|---|
| 模块导入 | — | **0.81 ms** | — |
| wasm 加载（`initSync`，57 MB） | < 200 ms | **13.21 ms** | ✅ |
| 初始化（`new WasmPhonemizer`，含词典就绪） | < 500 ms | **14.53 ms** | ✅ |
| **日语** 50 字 | < 2 ms | **0.4144 ms** | ✅ **有意义** |
| 中文 50 字（开箱） | < 2 ms | 0.0145 ms | ⚠️ **空操作**（透传） |
| **中文 50 字（+TONE3 词典）** | < 2 ms | **0.0766 ms** | ✅ **有意义** |
| 英语 50 字 | < 10 ms | 0.0140 ms | ❌ **空操作**（本构建无英语 G2P） |
| 堆内存 `heapUsed` | < 100 MB | **24.79 MB** | ✅ |
| `arrayBuffers` / `external` | — | 119.96 / 121.98 MB | 见注 |
| `rss` | — | 389.18 MB | 见注 |

```
名义     5/6 = 83%   ← 够到 80% 线
有意义   4/6 = 67%   ← 不达标（英语那一项测的是空操作）
```

> **内存注**：清单要求 `< 100 MB`，`heapUsed` 24.79 MB 通过。但 `arrayBuffers` 119.96 MB——那才是这个 wasm 的真实代价（57 MB 模块 + 约 60 MB wasm 线性内存，词典就住在里面）。浏览器扩展里更接近后者的量级，应据此预算。

### 5.1 与现有 JS 链对照（同机同样本）

| 语言 | wasm | 现有 JS 链（V0 同机基线） | 倍率 |
|---|---|---|---|
| 中文 | 0.0766 ms（+词典） | 0.0875 ms | wasm 快 **1.14×** |
| 日语 | 0.4144 ms | 0.1825 ms | wasm **慢 2.27×** |
| 英语 | — （空操作） | 3.8346 ms | 不可比 |

**日语反而更慢了 2.3 倍**（0.41 ms vs 0.18 ms），因为 jpreprocess + NAIST-JDIC 做的事比 kana2ipa 多得多（长音、拨音变体、无声化、音高）——这是**质量换来的**，不是退步。而且如 P6 §0.2 所述，**性能从来不是 P6 的理由**（预处理只占合成耗时的 0.009%–0.44%）。

**冷启动是真的好**：57 MB 的 wasm 编译+实例化只要 13 ms，因为 96% 是数据段而非代码。总冷启动 ~30 ms，远低于 P6 §0.4 的 100 ms 预算。这对「offscreen 文档被回收后重新冷启动」的场景是利好。

## 6. 对 P6 的含义

### 6.1 与 P6 spec 成功标准的逐条核对

| P6 §0.4 标准 | 实际情况 |
|---|---|
| 输出逐字符等于 JS 输出，或有记录的更优 | ❌ 三语无一逐字符相同；日语可论证为「更优」，中/英是透传 |
| 冷启动 ≤ 100 ms | ✅ 实测 ~30 ms |
| 只有**一个** `.wasm`，espeak 也在里面 | ❌ 只有一个 wasm，但**里面没有英语**，更没有 espeak；英语仍要另找方案 |
| 开箱即用，用户零下载 | 日语 ✅；**中文 ❌**（词典未发布，且格式不匹配） |
| §0.2 理由①：TN / FST | ❌ 没有。数字与拉丁文原样透传 |
| §0.2 理由②：日语汉字转换不再痛苦 | ⚠️ **部分**——jpreprocess 替代了 kuromoji，但输出是 piper-plus 自己的音素体系（PUA + 音高标记），不是 Kokoro 的 |

### 6.2 建议

1. **不要采用 `piper-plus` 作为 P6 的整体替代方案。** 它不是一个「三语 G2P 模块」：英语不在里面，中文要自己补词典+转格式，输出是 ID 而非音素串，音素体系是 piper-plus 自己的。适配工作量不小于自建。

2. **但日语这一块值得单独评估。** 这是本次唯一实打实的收获：一个**离线、零下载、质量高于现状**的日语 G2P（jpreprocess + NAIST-JDIC，BSD-3-Clause，无 GPL），冷启动 30 ms，单句 0.41 ms。它直接命中 P6 §0.2 的第二条理由（kuromoji 的持续痛苦：vendor + ESM 转换 + 17.8 MB 词典 + 读音要打补丁）。
   - 代价：57 MB wasm（但其中 55 MB 是日语词典；若只要日语，可考虑 `--no-default-features --features ja` 自行构建，体积不会小，因为词典是大头）。
   - 待办：把它的音素体系（PUA + 音高标记 + ASCII `g`）映射到 Kokoro 音素集，并逐条对照现有 kana2ipa 输出——**日语读音会变**（`こんにちは` 从 `ha` 变 `wa`），需要产品决策。

3. **中文不要指望这个包。** 音素体系不同（IPA+PUA vs 注音+数字），TN 缺失，词典要自己补且格式要自己转。若中文要迁 Rust，`lindera` + 自建 pinyin→注音映射（P6 spec §1.4 已实测 lindera 可用）比这个 wasm 更贴近目标。

4. **英语保持现状或另找方案。** 本次没有给出任何替代 espeak 的路径，GPL 风险不因 V1 而改变。

5. **值得上游反馈的两个缺陷**（若将来还会考虑这个包）：
   - npm 包漏发 `assets/pinyin_{single,phrases}.json`（2.7 MB），导致中文开箱不可用；
   - 上游那份词典是带调符号格式，而 `extract_tone` 只认行尾数字，两者不匹配（41,806/41,923 条带调符号，0 条带数字）；
   - 附带：`.d.ts` 关于 `language` 参数的注释与实测行为相反；`THIRD-PARTY-LICENSES.md` 关于词典「运行时下载」的陈述已过时。
