**日期**: 2026-10-01

**分支**: `p5-chinese-g2p`（从 `main` 切出）
**目标版本**: 0.5.0

## 0. 概述

### 0.1 目标

用户反馈 Kokoro 中文的**分词与多音字仍有瑕疵**。实测（§1.2）把这句话落成了
**5 处系统性偏差 + 一批具体错例**，其中「停顿/节奏怪」的根因不是模型也不是词典，
而是**我们喂进去的音素串格式与训练时的 G2P 不一致**。

本轮分两个阶段：

- **阶段 1（止血）**：把音素串的**格式**对齐到模型训练时的 G2P，并加一层
  **多音字补丁表**修掉实测错例。不动模型、不动架构，改动集中在
  `lib/models/phonemize/chinese.ts`。
- **阶段 2（升级）**：把模型从 **Kokoro v1.0（8 个中文音色，官方评级 D）**
  换到 **Kokoro v1.1-zh（100 个中文音色，专业录音数据集）**。
  这需要换 tokenizer（IPA → 注音符号）并移植官方前端 `ZHFrontend`。
  **运行时可行性已由 POC 验证**（§2.2）。

### 0.2 不包含

- ❌ 英文路径的任何改动（`english.ts` 不动）
- ❌ 云端 provider 的任何改动
- ❌ 日/西/法/印地/意/葡（v1.1-zh 的 vocab 里含英文 IPA，但本轮不接英文以外的语言）
- ❌ 词级高亮（Kokoro 不给时间戳，P4 §3.12 已定）
- ❌ 换用别的模型族（Piper/Kitten/MMS）

### 0.3 成功标准

| # | 标准 | 判据 |
|---|---|---|
| 1 | 阶段 1 的音素串与训练时 G2P **逐字符对齐**（除 §3.6 明示的例外） | 单测断言；对照脚本 `scripts/compare-legacy-g2p.py` 可复现。**试听页已在 s3 上证实可行**（ids 逐位相同） |
| 2 | §1.3 的错例**全部修正** | 每条错例一个单测 |
| 3 | 补丁表的**每条都真实生效** | 单测断言「去掉补丁表后输出会变」 |
| 4 | 阶段 1 的听感**不差于**修改前 | **用户试听**（V24）。这是唯一判据，见 §3.7 |
| 5 | 阶段 2 的模型在 offscreen 文档里**能跑**，且 `fp32` 不被 30 秒回收打断 | V26 |
| 6 | 阶段 2 的音素串能被 v1.1-zh tokenizer **全字符接受** | 单测断言 0 个未知字符 |

## 1. 问题：现状与实测偏差

### 1.1 现状实现

`lib/models/phonemize/chinese.ts` 的 `hanToIpa()`：

```ts
const syllables = pinyin(han, { toneType: 'num', type: 'array', nonZh: 'removed' });
return syllables.map((s) => syllableToIpa(s, context)).join(' ');
```

即：把**整个汉字段**交给 `pinyin-pro` 一次性注音（它内部用词典 + 分词做多音字消歧），
逐字查 `pinyin-table.json` 得 IPA，**每个音节之间插一个空格**。

### 1.2 五处系统性对齐偏差（实测，2026-10-01）

用 Python 复现了**模型训练时真正用的 G2P**——misaki 的 legacy 路径
（`jieba.lcut` 分词 + `lazy_pinyin` + `pinyin_to_ipa`），与我们逐句对比：

样本：`今天天气不错，我们去公园散步吧。`

| | 音素串 |
|---|---|
| **legacy（训练时）** | `ʨi→ntʰjɛ→ntʰjɛ→nʨʰi↘ pu↘ʦʰwo↘, wo↓mən ʨʰy↘ kʊ→ŋɥɛ↗n sa↘npu↘ pa.` |
| **我们（现状）** | `ʨi→n tʰjɛ→n tʰjɛ→n ʨʰi↘ pu↗ ʦʰwo↘ , wo↓ mən ʨʰy↘ kʊ→ŋ ɥɛ↗n sa↘n pu↘ pa .` |

| # | 偏差 | legacy | 我们 | 性质 |
|---|---|---|---|---|
| **A** | **空格密度** | **词内连写、词间空格** | **每音节一空格** | 100% 系统性 |
| **B** | **标点前空格** | 标点紧跟音素（`ʨje↘.`） | `ʨje↘ .` | 100% 系统性 |
| ~~C~~ | ~~「一/不」变调~~ | **词典里 56% 变调、44% 原调** | 规则化地全变调 | **不是偏差，已从清单里去掉** |
| **D** | **`̯` U+032F** | **显式删除** | 保留（`ʦai̯↘` vs `ʦai↘`） | 系统性 |
| **E** | 多音字 | `xwa↗n`（huán） | `xai̯↗`（hái） | 个别词 |

**A + B 就是「断句/停顿/节奏怪」的根因。** 模型训练时看到的词边界是
「一个词一条」，我们给的是「一个字一条」——边界密度是训练时的 3–5 倍。
这不是模型的问题，也不是词典的问题。

#### C 的修正（2026-10-01 实测）：它不是偏差，已从清单里去掉

本节最初把 C 写成「legacy 不做变调，我们做了 → 应该关掉」。**那个前提是错的。**

在**干净进程**里（不 import misaki，否则 `ZHFrontend` 会加载 `large_pinyin` 污染全局词典）
实测 pypinyin 的内置词典：

```
一个 → yi2 ge4  ✅变调     一样 → yi1 yang4  ❌原调（规则上应 yí yàng）
一定 → yi2 ding4 ✅变调     一件 → yi1 jian4  ❌原调
一半 → yi2 ban4  ✅变调     一天 → yi1 tian1  ❌原调
不是 → bu2 shi4  ✅变调     不错 → bu4 cuo4   ❌原调（规则上应 bú cuò）
```

量化：词典里「一/不 + 字」的两字词条共 **294 条，166 条（56%）已变调、128 条（44%）原调**，
分布是任意的。

**所以 legacy 不做变调*规则*，但它的*词典*里有一部分词条是变调后的。**
后果：**没有任何一个 `toneSandhi` 设置能对齐 legacy** —— 关掉只能对上那 44%，
并错开 56%。试听页上的 ids 摘要把这一点测得很难看：

| 变体 | s1（一个） | s2（一石二鸟） | s3（还书） |
|---|---|---|---|
| 对齐 A+B+D（**保留**变调） | ✅ 与 legacy 逐位相同 | ❌ | ❌ |
| 对齐 A+B+C+D（**关掉**变调） | ❌ | ✅ 逐位相同 | ❌ |

再叠上 §1.6（2）——**声调箭头几乎不改变音高**——结论很清楚：

> **C 不列入阶段 1。保持现状（`toneSandhi: true`）。**
> 理由：① 关掉并不能对齐；② 保留是语言学上正确的那个选择；
> ③ 实测它对音频几乎无影响。
> **真正买到对齐的是补丁表，不是变调开关**（s3 加上补丁后与 legacy 逐位相同）。

（原 C 的解释保留在此供对照：`pinyin-pro` 的 `toneSandhi` **默认 `true`**，我们没关。）

D 的来源：`misaki/zh.py` 的 `legacy_call` 结尾有
`result.replace(chr(815), '')`——它**在 Python 层就删掉了 U+032F**。
（另一个组合符 `̩` U+0329 双方都保留，靠 tokenizer 的 normalizer 处理。）

### 1.4 为什么不能靠「换个引擎」解决

把 `pypinyin`（内置词典）与 `pinyin-pro` 在 159 条语料上对比，**互有胜负**：

- **pypinyin 对、pinyin-pro 错**：还书、着装、咖喱、乳臭、冲床、相片、朝鲜、教书
- **pinyin-pro 对、pypinyin 错**：削苹果（`xue1`✗）、一行白鹭（`xing2`✗）、累赘（`zhui4`✗）、
  华为（`wei2`✗）、卷子（`juan3`✗）、覃（`tan2`✗）、阚（`han3`✗）

两者都是「分词 + 词典」，准确率同档，**换引擎收益有限**。真正的解法是补词典（§3.3）。

### 1.5 为什么阶段 1 **不能**加三声连读变调和儿化

实测我们**完全不做**三声连读变调（18/18 缺：`你好`→`ni3 hao3`）和儿化
（13/13 缺：`花儿`→`hua1 er2`）。看起来很该修，**但方向是错的**：

- 我们用的是 **v1.0 的 IPA tokenizer**（`tests/unit/models/kokoro-vocab.ts` 里
  注音符号数量 = 0，且有 `↓→↗↘`）。
- v1.0 的 8 个中文音色在官方 `VOICES.md` 里评级 **D**，训练时用的 G2P 就是
  misaki 的 **legacy 路径**——**那条路径本身不做变调、不做儿化**。
- 模型学到的映射是「**原调音素序列 → 实际变调的音频**」。
  我们加变调/儿化等于**偏离训练分布**。

**只有 v1.1-zh 才需要它们**（它的 `ZHFrontend` 就做变调与儿化，见 §4.3）。
阶段 1 **不碰变调**（见 §1.2 C 的修正）；阶段 2 让 `ZHFrontend` 接管这一层。

### 1.6 两个模型侧的实测限制（影响阶段 1 的预期收益）

搭试听页（`poc/kokoro-zh-samples/`）的过程中顺手量了两件与「格式对齐到底能带来多少改善」
直接相关的事。**两条都不是音素串的问题，是 v1.0 模型本身的问题。**

#### （1）v1.0 在逗号处不暂停

句子 `一石二鸟，一举两得。`，量句中是否存在 ≥40ms 的低能量段：

| clip | 句中 ≥40ms 静音段 |
|---|---|
| v1.0 的七个格式变体（含「现状」） | **一个都没有** |
| v1.0 的 legacy 参考 | 80ms |
| v1.1-zh 官方 `ZHFrontend` | **100ms** |
| v1.1-zh 2a 式 | 70ms |

喂进去的都是同一个 `, `（ASCII 逗号 + 空格）。**同一个 token，v1.1-zh 会停顿，v1.0 不会。**

含义：**偏差 B（标点）的修复对 v1.0 的收益可能有限** —— 我们把标点放到对的位置，
模型也未必据此停顿。这是「停顿怪」的第二个成因，而且是阶段 1 **改不动**的那一个。

> 前提：这是用「低能量段」判定的，若停顿处底噪高于阈值会漏检。
> 但同一个检测器在 v1.1-zh 上能报出 100ms，说明它本身是工作的。

#### （2）声调箭头几乎不改变音高

同一句话（`一石二鸟`），只把第一个「一」的箭头从 `i→` 换成 `i↘`：

- 波形相关性 **0.23** —— 输出**确实变了**（运行时的自身噪声是 0.994，所以这是真实差异，不是抖动）
- 但每音节中位基频是 `333/258/293/203` vs `333/264/289/205` Hz —— **差几 Hz，实质相同**

单音节上四个声调（`i→`/`i↗`/`i↓`/`i↘`）也测不出干净的「平 / 升 / 降升 / 降」
对应关系，v1.1-zh 同样不干净。

**这条结论要谨慎读**：单音节是分布外输入，**不能**说明句子里的行为。它能确定的是：

1. **偏差 C（要不要关变调）无法用基频机械地判定** —— 只能靠耳朵。
   §3.7 已经把听感定为唯一判据，这里只是补上了「为什么必须如此」。
2. 这是 v1.0 中文音色 **D 级的一个具体表现**：音色的问题不只是「不好听」，
   而是**声调实现不可靠**。这比 §4.1 的「评级 D」更能说明为什么阶段 2 值得做。

## 2. 关键事实：两个模型是两套 tokenization

### 2.1 v1.0 vs v1.1-zh

`hexgrad` 名下只有 3 个仓库：`Kokoro-82M`(v1.0)、**`Kokoro-82M-v1.1-zh`（最新，2025-02-26）**、
`kLegacy`(v0.19)。**没有 v1.2**；`kokoro`/`misaki` 的 PyPI 都是 0.9.4。

| | v1.0（现在用的） | v1.1-zh |
|---|---|---|
| vocab 大小 | 115 | **172** |
| 音素体系 | **IPA** | **注音符号（38 个）** |
| 声调编码 | **箭头 `↓→↗↘`** | **数字 `1`–`5`** |
| 声调箭头数量 | 4 | **0** |
| 词分隔符 | 空格 | **`/`** |
| 儿化 | 无（`er` 单独成音节） | **`R`** |
| 中文音色 | 8 个，官方评级 **D** | **100 个**（龙猫数据专业录音） |
| ONNX | `onnx-community/Kokoro-82M-v1.0-ONNX` | `onnx-community/Kokoro-82M-v1.1-zh-ONNX` |

v1.1-zh 的 vocab 里甚至保留了 PaddleSpeech 那套遗留汉字映射
（`十 月 压 言 阳 要 阴 应 用 又 中 穵 外 万 王 为 文 瓮 我 元 云`）——
这证明它的 vocab 是照 `ZHFrontend` 的**实际输出**建的。

**这不是「同一个模型的新权重」，是另一套前端 + 另一套音素集。**

### 2.2 POC 结论：运行时可行，而且快 8–10 倍

POC 代码在 `poc/kokoro-v11zh-webgpu/`（**一次性 spike，阶段 2 决策落地后删除**），
完整数据与复现步骤见其 `README.md`。Apple M 系列 / Chromium / WebGPU(`metal-3`)：

| combo | session | RTF（4.25s / 7.33s / 19.6s） | 与 Python 参考的相关性 | 判定 |
|---|---|---|---|---|
| **webgpu/fp32** | 748 ms | **0.100 / 0.104 / 0.103** | 0.993–0.995（能量包络 0.9998） | ✅ 同一句话 |
| wasm/fp32 | 433 ms | 1.079 / 1.105 / 1.084 | 0.992–0.995 | ✅ |
| webgpu/fp16 | 438 ms | 0.062 / 0.060 / 0.057 | **NaN** | ❌ **全 NaN** |
| wasm/fp16 | 738 ms | 1.035 / 1.036 / 1.043 | **NaN** | ❌ **全 NaN** |

三条结论：

1. **RTF 在三种长度上平坦** → 不是短输入的固定开销假象，20 秒的段落 2 秒合成完。
2. **比 WASM 快 8–10 倍**（两次完整运行的比值分别是 10.5x 与 7.8x；绝对值会随机器负载
   在 0.10–0.14 之间波动，**比值稳定**）。
3. **`fp16` 是陷阱**：全场最快（RTF 0.057）却产出纯 NaN，而且在 Python CPU 上也坏
   （与 fp32 相关性仅 **0.087**、rms 减半、输出长度不稳定）。**只能用 `fp32`（323.6 MB）**。

附带：**session 初始化从 v1.0 的 ~12s 降到 ~750ms**。P4 §0.1 里「必须预取、必须诚实
显示进度」的结论对 v1.1-zh 大幅松动——20 秒的段落 2 秒出音频，首句延迟的瓶颈
不再是合成，而是模型加载。

**POC 验证过但尚未验证的**：POC 跑在普通页面里，**不是 MV3 offscreen 文档**
（V26）。324 MB 的模型在 offscreen 里的内存表现、以及是否会被 30 秒回收打断，
需要单独验。

## 3. 阶段 1：对齐 legacy 格式 + 精准补丁

### 3.1 改动点（全部在 `lib/models/phonemize/`）

| # | 改什么 | 怎么改 |
|---|---|---|
| 1 | 删 `̯` U+032F | 音节 IPA 结果 `.replaceAll('\u032F','')` |
| 2 | 标点前不加空格 | `ChinesePhonemizer.phonemize` 的拼接逻辑（§3.2） |
| 3 | 词内连写、词间空格 | 用 **jieba** 取词边界（§3.2） |
| 4 | 多音字补丁层 | 新文件 `patches.ts` + `patches.json`（§3.3） |

**这 4 项互相独立，可以逐项回滚。** 这是刻意的：§3.7 说明格式改动是**推断**，
唯一判据是听感，所以每一项都要能单独撤销。

> **原第 1 项「关掉 `toneSandhi`」已撤销。** 理由见 §1.2 C：legacy 的词典自己就不一致
> （56% 变调 / 44% 原调），关掉并不能对齐；再叠上「声调箭头几乎不改变音高」（§1.6），
> 这一项既无收益又无意义。

### 3.2 词边界：`jieba-wasm`

`pinyin-pro` 的 `segment()` API **不暴露词边界**——实测 `format: 1/4/7/8/9` 全部按**单字**
返回（`你好世界` → `["你","好","世","界"]`）。它内部有分词（用于多音字消歧）但不暴露结果。

#### 为什么最终选了 jieba（而不是零体积的 `Intl.Segmenter`）

最初的选型是 `Intl.Segmenter`（零体积），但实测下来它太差，而且换 jieba 之后
**阶段 1 与阶段 2b 共用同一份依赖**（阶段 2b 的儿化规则需要词性）。

| 方案 | 体积 | 分词质量 | 词性 | 结论 |
|---|---|---|---|---|
| **`jieba-wasm`** | **3.83 MB wasm**（unpacked 15.4MB 是打包了 4 份 deno/nodejs/web/bundler 副本，进包只有一份） | **与训练时一致** | ✅ `tag()` | ✅ **采用** |
| `Intl.Segmenter` | 0 | 中等（明显更差） | ❌ | 回退方案（§5 V23） |
| 全连写（不分词） | 0 | — | ❌ | ❌ 丢失词边界，训练数据里是有的 |

`Intl.Segmenter` 的实测质量（对比 jieba）：

| 句子 | jieba（= legacy） | `Intl.Segmenter` |
|---|---|---|
| 他是一个工程师 | `他\|是\|一个\|工程师` | `他是\|一个\|工程\|师` |
| 中国人民银行 | `中国人民银行\|今天\|发布\|了` | `中国\|人民\|银行\|今天\|发布\|了` |
| 我们的产品支持中英文混合输入 | `…\|支持\|中英文\|混合输入` | `…\|支持\|中\|英文\|混合\|输入` |

**jieba 的价值不只是「更好」，是「同一份」**：misaki 的 legacy 路径就是
`jieba.lcut`，用同一个分词器就不需要再讨论「词边界能不能对齐」这个问题。

#### `hmm` 参数是 load-bearing 的

`jieba-wasm` 用的是 **jieba-rs 的词典**，与 Python jieba 的 `dict.txt` 不是同一份。
差异靠 `hmm` 开关放大或掩盖：

```
cut('他昨天去图书馆还书了。', false) → [...,'图书馆','还','书','了','。']   ❌ 与 Python 不一致
cut('他昨天去图书馆还书了。', true)  → [...,'图书馆','还书','了','。']     ✅
```

Python 的 `jieba.lcut(segment, cut_all=False)` 的 **HMM 默认是开的**，所以对应的是
`cut(text, true)`。实测 **24 句 24 句完全一致**；而用 `hmm: false` 时第一句就分叉。

> **实现时必须显式传 `true`。** 忘了传，得到的是一个「看起来能跑」的分词器，
> 只在部分词上默默与训练时不一致 —— 而「还书」恰好就是其中一个，
> 它又是补丁表里的第一条。

#### 其它 API

```ts
cut(text, hmm?)            // 分词
cut_all(text)              // 全模式
tag(sentence, hmm?)        // 词性标注 → {word, tag}[]   ← 阶段 2b 的儿化规则用
add_word(word, freq?, tag?)// 加词
with_dict(dict)            // 整体换词典
```

实测 `tag()` 可用（`{word:'图书馆', tag:'n'}`），所以阶段 2b 的
`pos in {a, j, nr}` 不需要额外依赖。注意 **HMM 发现的词词性是 `x`**
（例：`还书` → `x`），阶段 2b 用词性做儿化判定时要考虑这一点。

#### 实现要点

- **必须验 V23**：`jieba-wasm` 在 offscreen 文档里可用、初始化耗时、能否进包。
  按 P4 的教训（`chrome.storage` 在 offscreen 里是 `undefined`），**先验再用**。
- 按词的**字符长度**切分 `pinyin-pro` 返回的音节数组：每个词对应
  `word.length` 个音节，**词内 `join('')`，词间 `join(' ')`**。
- 这依赖「音节数与字符数一一对应」这个既有不变量（`hanToIpa` 已在检查，
  不满足时抛 `UnknownSyllableError`）。
- **分词器只负责词边界，读音仍来自 `pinyin-pro`**（后者用自己的内部分词做多音字消歧）。
  两者不一致只影响韵律，不影响读音。

#### 标点（改动 #2）

`legacy_call` 是**按「汉字段 / 非汉字段」交替**、**把非汉字段原样追加**的，
所以标点**紧跟**在前一个音素后面，空格来自标点**后面**
（`map_punctuation` 把 `，` 换成 `", "`，是「标点 + 空格」）。

我们现在的 `parts.join(' ')` 会在**标点前**插一个空格，这是 B 类偏差的来源。

**精确规则**（不要写成「段之间加空格」这种模糊话，那是错的）：

> **所有段直接拼接，不在段之间插入任何空格。** 音素串里空格的唯一来源是：
> ① 汉字段**词与词之间**的那个空格（本节前半）；
> ② 非汉字段**原有的**空格（`mapPunctuation` 已在标点后补了空格，原文里
> ` API ` 两边的空格也是）。

这条规则要求 `keepPunctuation` **不再 `trim()`**（现在的实现会 `trim()`，
所以 `" API "` 会变成 `"API"`，直接拼接后会粘到相邻汉字上）。
收尾的 `.replace(/\s+/g, ' ').trim()` 仍然保留，由它负责折叠与首尾清理。

**测试要点**：`你好世界。` 必须以 `ʨje↘.` 结尾，**不是** `ʨje↘ .`；
而 `这里有个 API 接口。` 必须保留 `API` 两侧的空格。

### 3.3 多音字补丁层

**为什么不用 `pinyin-pro` 的 `customPinyin` / `addDict`**：实测两者在
`toneType: 'num'` 下**都坏了**——

```js
customPinyin({ '还书': 'huan2 shu1' });
pinyin('还书', { toneType: 'num', type: 'array' });  // → ['huan20', 'shu10']
```

注入的拼音串被当成「无声调文本」，声调补 `0` 后被再拼一次。`addDict` 同样。
（`toneType: 'symbol'` 下输出 `'huan2 shu1'` 原样，说明它根本没解析声调。）

所以**自建补丁层**，在 `pinyin-pro` 返回音节数组后**按字符位置覆盖**：

```ts
// patches.json: { "还书": "huan2 shu1", "着装": "zhuo2 zhuang1", ... }
const syllables = pinyin(han, { toneType:'num', type:'array', nonZh:'removed' });
applyPatches(han, syllables);   // 最长匹配，原地覆盖
```

理由：可控、可测、无体积开销、不依赖有 bug 的上游 API。

**两条硬约束**（要写进单测）：

1. **音节数不变**：补丁是「按字符位置覆盖」，命中词条的长度必须等于它替换的音节数。
   这条不变量一破，`hanToIpa` 的「音节数 == 字符数」检查就会误报成
   `pinyin-pro` 读不出字。
2. **重叠时最长匹配优先**：`项目` 与 `项目的` 同时命中时取后者。
   表里**不允许**存在两条同长度、同起始位置的冲突条目——要有测试断言这一点。

**补丁表的来源与边界**（这是本节的关键决定）：

- **v1（本轮）**：**手工整理的高频错例**——§1.3 的全部错例 + 姓氏表 + 「的/地/得」。
  规模目标 **≤ 500 条**，每条都要有来源依据（实测错例或权威词典）。
  ⚠️ **不能拿 `pypinyin` 当唯一依据**：实测「掉色」（`diao4 se4`）与
  「一哄而散」（`yi1 hong4`）**两个引擎都错**，这两条必须查权威词典。
- **v2（本轮不做）**：从 `pypinyin` 的 `large_pinyin` **离线生成差异表**。
  实测：该词典 **411,957 条、13.8MB 源码，且 100% 都是含多音字的条目**
  （无法靠「只留含多音字的条目」来缩小）。与 `pinyin-pro` 的差异率 **7.52%**
  → 外推约 **3 万条**。但其中**大量是「两边都合理」的差异**（变调、轻声），
  **不能直接当修正表用**，必须先分类再人工抽检。
  **本轮不做**：3 万条需要人工审核，收益不确定，而 v1 的几百条已经覆盖了实测错例。

**姓氏怎么处理**：`pinyin-pro` 的 `mode:'surname'` 是全局开关，用了会把
「单于」「解放」这类词也改掉。所以**不改全局模式**，而是把姓氏放进补丁表——
但需要一个**触发条件**，否则「单」在任何地方都读 `shan4`。

**决定：用「姓氏后接称谓/职务」的有限模式**匹配：

```
(单|仇|解|查|区|朴|曾|华|任|燕|纪|乐)(老师|先生|女士|医生|教授|经理|总|同学|主任|校长|师傅|律师|记者)
```

理由：这是可枚举、可测试、误伤面小的规则；不做通用人名识别（那需要 NER，
与「补丁表」的复杂度不是一个量级）。**误伤检查**：这条规则不能命中
「单于」「解放」「查一下」等常见非姓氏搭配——要有反向测试。

### 3.4 数据流（阶段 1 之后）

```
text
  → numbersToHan（不变）
  → mapPunctuation（不变）
  → splitRuns
      Han   → pinyin（不改 toneSandhi）→ 补丁层覆盖 → 逐音节查表 → 删 U+032F
            → jieba 切词 → 词内 join('') / 词间 join(' ')
      Latin → espeak（不变）
      other → keepPunctuation（**去掉 trim**，见 §3.2）
  → 拼接：**所有段直接拼接**，空格只来自「词间」与「非汉字段原有空格」
```

### 3.5 测试

- **现有断言全部要改**：`phonemize.test.ts` 里写死了
  `'ni↓ xau̯↓ ʂɻ̩↘ ʨje↘'`，词内连写后会变成 `'ni↓xau↓ ʂɻ̩↘ʨje↘'`（同时 `̯` 被删）。
- **新增**：
  - **不**断言 `toneSandhi` —— 它不再属于阶段 1（§1.2 C）
  - 分词器：`cut(text, true)` —— 用一个 `hmm` 一关就分叉的句子钉住它（§3.2）
  - U+032F 已删：输出不含 `\u032F`
  - 词边界：`你好世界` → `ni↓xau↓ ʂɻ̩↘ʨje↘`（两个词，词内无空格）
  - 标点紧邻：`你好世界。` → 以 `ʨje↘.` 结尾，**不是** `ʨje↘ .`
  - 补丁表：§1.3 每条错例一个用例
  - **补丁表非空断言**：每条补丁都必须在**不加载补丁表**时产出不同结果。
    否则说明 `pinyin-pro` 升级后这条已经不需要了——**让陈旧的补丁条目响亮地失败**，
    而不是悄悄留着。
  - 姓氏模式的正向 + **反向**用例（`单于`/`解放`/`查一下` 不受影响）
- **对照脚本** `scripts/compare-legacy-g2p.py`：用 Python 复现 misaki legacy
  路径（`jieba` + `lazy_pinyin` + 我们那张表），与 `hanToIpa` 的输出逐句对比。
  **这是「对齐」这个目标唯一可自动化的证据。** 脚本依赖固定版本，写进注释。
  脚本必须实现 §3.6 的两条归一化，否则它会报一堆「假失败」。

### 3.6 对齐的例外

对齐目标是**逐字符一致**，但有两处**明示的例外**，因为它们不可消除：

1. **读音来源不同**：legacy 用 pypinyin 的词典，我们用 `pinyin-pro` 的词典。
   词边界已经对齐（两边都是 jieba，§3.2），所以剩下的差异**全部是词典差异**
   （例：还书 → `xwa↗n` vs `xai̯↗`）—— 而这正是补丁表要消掉的东西。
   → 对照脚本要能把「词典差异」与「格式差异」分开报，并标出补丁生效的位置。
2. **补丁表**：补丁表**故意**偏离 legacy（legacy 也错，比如它还读不对「削苹果」）。
   → 对照脚本要能标出「这里是补丁生效」而不是报成失败。

### 3.7 风险与回滚

**最大的风险：格式改动是「更贴近训练分布」的推断，而 P4 §1.1.1 的教训是
「仓库里有文件」不等于「运行时路径能用」。**

缓解：

- 5 项改动互相独立，**逐项可回滚**（§3.1）。
- **唯一判据是听感**（V24）。用户听同一段文本的修改前后两版。
- 如果听感变差，按「A → B → C → D → E」的顺序**从最可疑的开始回滚**：
  A（词边界）的影响面最大，E（补丁）最小。
- 对照脚本提供「我们离训练分布有多远」的可量化证据，但**不能替代听感**。

## 4. 阶段 2：升级到 Kokoro v1.1-zh

### 4.1 为什么要升级

v1.0 的 8 个中文音色是**官方评级 D**（`VOICES.md` 里中文那一栏 8 个全是 D，
英文有 A/A-/B 各档）。v1.1-zh 是**用 100 小时以上专业录音数据集重训**的，
100 个音色。**音色质量的上限在 v1.0 那里就封死了**，G2P 修得再准也救不了。

### 4.2 运行时（已由 POC 验证）

- 模型：`onnx-community/Kokoro-82M-v1.1-zh-ONNX`，**只用 `onnx/model.onnx`（fp32, 323.6 MB）**。
- 执行：`executionProviders: ['webgpu']`（RTF ≈ 0.10），回退 `wasm`（RTF ≈ 1.08）。
- **`fp16` 禁止使用**（§2.2），注册表里不提供该档位——不要留一个「更快但坏」的选项。
- 输入签名与 v1.0 相同：`input_ids` int64[1,N]、`style` float32[1,256]、`speed` float32[1]；
  输出 `waveform` float32[N] + `duration` int64[1]。
- 音色 `.bin` = **510 × 256 float32**（522,240 字节），选行公式
  `clamp(len(input_ids) - 2, 0, 509)`（`-2` 来自 tokenizer 的
  `TemplateProcessing` 会前后各加一个 `$`，id = 0）。
- **注意**：v1.0 的档位表是按「更小/更快」排的（q8/fp16/fp32）。v1.1-zh 的
  `q4`(325MB)/`q4f16`(158MB)/`bnb4`(325MB) 并不比 fp32 小，`int8/quantized/uint8`
  都是 121.5MB 但**未经测试**。本轮**只提供 fp32 一档**，把「档位」概念先收起来。

### 4.2.1 ⚠️ 模型不吃文本：直接喂中文会**静默**产出错音（实测）

**结论：必须有外部注音管线，没有第二条路。** 三条证据：

1. **模型侧**：ONNX 唯一的文本侧输入就是 `input_ids`，没有文本编码器。
2. **官方侧**：参考实现 `samples/make_zh.py` 走的是
   `KPipeline(lang_code='z', repo_id='hexgrad/Kokoro-82M-v1.1-zh')`，
   它内部就是 misaki 的 `ZHG2P(version='1.1')`。**官方路径自己就带 G2P。**
3. **陷阱侧**：ONNX 仓库的元数据是 `library_name: transformers.js` +
   `pipeline_tag: text-to-speech`，所以 `pipeline('text-to-speech', ...)` 看上去
   应该能直接用。**不能** —— transformers.js 没有 G2P，它会把原始文本直接喂给 tokenizer。

而 tokenizer **不会报错**：它的 normalizer 保留集合里**显式列了 21 个汉字**
（`万中为云元十压又外应我文月王瓮用穵要言阳阴`）——因为它们正是 `ZH_MAP` 里
某些韵母的符号。所以汉字**能穿过 normalizer 并映射到真实 id**。实测：

| 输入（原始中文） | normalizer 保留 | ids | 输出时长 | 与正确读音的相关性 |
|---|---|---|---|---|
| `今天天气不错，我们去公园散步吧。` | `我`（1/16 字） | `[0,168,0]` | 0.50s（应 4.25s） | — |
| `中文` | `中文` | `[0,155,166,0]` | 0.62s（应 0.95s） | **+0.121** |
| `我` | `我` | `[0,168,0]` | 0.50s（应 0.72s） | **+0.151** |
| `中华人民共和国` | `中`（1/7 字） | `[0,155,0]` | 0.55s | — |
| `人工智能技术正在快速发展` | **（空）** | `[0,0]` | 0.38s | — |

**`中文` 的 `[155, 166]` 正是 `ong` 与 `uen` 两个**裸韵母**的符号** —— 模型会把它
读成两个韵母，**不是** zhōng wén。

相关性 **+0.12～+0.20** 与「fp16 坏掉」时的 0.087 同一量级：输出与正确读音基本无关，
但**有正常音量、正常时长、不报错**。这是和 fp16 同一类的失败模式。

**硬要求（要写成单测，阶段 1 与阶段 2 都要）**：

> **进 tokenizer 的音素串，除已知会被 normalizer 剥掉的两个组合符
> （`̯` U+032F、`̩` U+0329）之外，其余字符必须全部在词表里。**

两条理由都是实测踩出来的：

1. **汉字**：vocab 里有 21 个汉字（见上表），混进去一个不会报错，只会静默变错。
2. **全角标点**：`，` `。` 不在词表里，会被**静默剥掉** —— 而标点正是停顿的来源，
   丢一个逗号就丢一次停顿。（这个 bug 在试听页的 harness 上真发生过一次，
   见 §7 T4 的注记。它把一个「应该是训练目标」的对照 clip 变成了缺停顿的错误样本，
   而任何断言都没有拦住它。）

阶段 1 的 IPA 路径与阶段 2 的注音符号路径都要断言这一点。

### 4.2.2 官方参考里的 speed 调度（v1.1-zh 会「赶」）

`samples/make_zh.py` 里有一段显式 HACK：

```python
# HACK: Mitigate rushing caused by lack of training data beyond ~100 tokens
# Simple piecewise linear fn that decreases speed as len_ps increases
def speed_callable(len_ps):
    speed = 0.8
    if len_ps <= 83:
        speed = 1
    elif len_ps < 183:
        speed = 1 - (len_ps - 83) / 500
    return speed * 1.1
```

即：`len_ps ≤ 83` → **1.1**（比 1.0 还快）；`83 < len_ps < 183` → 线性降到 1.03；
`len_ps ≥ 183` → **0.88**。官方注释说这是为了缓解「超过约 100 token 后训练数据不足导致的赶」。

**决定**：阶段 2a 照抄这条调度（而不是恒定 `speed = 1.0`），`len_ps` 取**音素字符数**。

⚠️ **POC 用的是恒定 `speed = 1.0`**（四个 combo 用同一个 speed，所以 POC 的**运行时对比**
依然成立），但**它的输出时长不是官方推荐的时长**，不能拿 POC 的时长当验收基准。

### 4.3 G2P：移植 `ZHFrontend`

v1.1-zh 的官方前端是 misaki 的 `ZHG2P(version='1.1')` → `ZHFrontend`，
它是 **PaddleSpeech 的 `zh_frontend.py` 的移植**（Apache-2.0），依赖：

| 依赖 | 作用 | JS 侧怎么办 |
|---|---|---|
| `jieba.posseg` | 分词 **+ 词性**（词性用于儿化规则：`pos in {a, j, nr}`） | **`jieba-wasm` 的 `tag()`** —— **已实测可用**（§3.2），且它就是阶段 1 已经在用的那份依赖 |
| `pypinyin` 的 `large_pinyin` | **411,957 条**短语拼音词典（13.8MB 源码） | ❌ 不可直接移植，见下 |
| `pypinyin` 的 `load_single_dict` / `load_phrases_dict` | 少量人工修正（`地 → de,di4` 等） | 进补丁表 |
| `ToneSandhi`（`tone_sandhi.py`，**385 行纯规则**） | 三声连读、「一/不」变调、轻声、`pre_merge_for_modify` | ✅ **可移植**（纯规则 + 词表） |
| `_merge_erhua`（~40 行） | 儿化：`儿` 并入前音节成 `R` | ✅ **可移植** |
| `ZH_MAP` | 拼音（声母 + 韵母 + 声调）→ 注音符号 | ✅ 静态表，**从我们已有的生成脚本派生** |

**`large_pinyin` 是阶段 2 最大的未知数。** 实测它 411,957 条、13.8MB 源码，
**100% 都是含多音字的条目**，无法靠「只留含多音字的条目」缩小。
三条路：

1. **离线生成「差异表」**（推荐）：只保留「与 `pinyin-pro` 输出不同」的条目 →
   实测差异率 7.52% → 约 **3 万条 / 约 900KB JSON（gzip 后约 300KB）**。
   需要分类剔除纯变调差异，并人工抽检。
2. **全量移植**：13.8MB，❌ 不可接受。
3. **不移植**：接受 `pinyin-pro` + 阶段 1 的补丁表。最省事，但**放弃了 v1.1-zh 的
   前端保真度**——而保真度正是阶段 2 的目的之一。

**决定：走 1，并把体积与抽检结论作为 V25 的一部分。**

### 4.4 阶段 2 分两步落地（重要）

因为 `ZHFrontend` 的移植量（jieba 词性 + 3 万条词典 + 385 行变调 + 儿化）**远大于**
模型与 tokenizer 的替换，把它拆开：

**2a — 换模型 + 换 tokenizer（小，先做）**

- 注册表加 v1.1-zh 模型（fp32 单档），换 100 个音色的表。
- 生成新表 `音节 → 注音符号`（用**同一个生成脚本** + pypinyin 的
  `to_initials` / `to_finals(strict=True)`，与 `pinyin-table.json` 同源）。
- 输出格式改为 `注音符号 + 数字声调`，词间用 `/`，**重新打开变调**（§1.5）。
- **speed 调度照抄官方参考**（§4.2.2），不再恒定 1.0。
- **不做**儿化、不做词性、不做 `large_pinyin`。

**2a 的已知缺口**（它拿到的音素串**不是** `ZHFrontend` 的输出，差异要写清楚，
免得日后当成 bug 查）：

| 缺口 | 原因 |
|---|---|
| **没有三声连读变调** | `pinyin-pro` 的 `toneSandhi:true` **只做「一/不」**，不做三声连读（实测 `你好` → `ni3 hao3`）。而 `ZHFrontend` 做（`ㄋㄧ2ㄏㄠ3`） |
| **没有儿化** | `ZHFrontend` 的 `_merge_erhua` 把「儿」并入前音节成 `R`；我们只会输出独立的 `er` 音节 |
| **词边界来源** | legacy 用 jieba，我们**也用 jieba-wasm**（§3.2）—— 所以这一项**不再是例外** |
| **没有词级读音修正** | 缺 `large_pinyin` 的 41 万条短语 |

**2a 的预期与风险**：正因为有这四个缺口，2a 的音素串与 `ZHFrontend` 差得不算少。
按 §1.5 的逻辑，这**可能**让音质不达预期。所以 **2a 必须由用户试听（V27）后再决定
2b 是否上**——如果 2a 已经明显好于 v1.0，2b 可以降级为「按需做」；如果 2a 不达预期，
2b 的 G2P 就是关键路径。

**2b — 移植 `ZHFrontend`（大，按需）**

- `ToneSandhi` 规则 + 儿化（纯规则，可移植）
- `jieba-wasm` 的词性标注（V25）
- `large_pinyin` 差异表（§4.3 方案 1）
- 逐句与 Python 版 `ZHFrontend` 对照（与阶段 1 §3.5 的对照脚本同一思路）

### 4.5 与阶段 1 的关系

**阶段 1 的改动不是白做的，但有一项会被阶段 2 改掉：**

| 阶段 1 的改动 | 阶段 2 怎么办 |
|---|---|
| #1 删 U+032F | **不再适用**：注音符号体系里没有这个字符 |
| #2 标点紧邻 | **保留**（`ZHFrontend` 的输出里标点也是紧邻的） |
| #3 词内连写/词间空格 | **改成 `/` 分隔**（v1.1-zh 用 `/`，不是空格） |
| #4 补丁表 | **保留并扩展**（阶段 2 的词典本身就是补丁表的放大版） |

> **变调不在这个表里** —— 阶段 1 不改它（§1.2 C 的修正），阶段 2 交给 `ZHFrontend`。
>
> **分词器则完全不用改**：`jieba-wasm` 同时是阶段 1 的词边界来源和阶段 2b 的
> 词性来源（§3.2、§4.3），一个依赖盖两阶段。

## 7. 任务分解

> **范围说明**：本 spec 覆盖两个阶段，**不是一份实现计划能装下的**。
> 预期拆成三份计划，每份做完都是一个可发布的中间状态：
>
> | 计划 | 任务 | 交付后可发布？ |
> |---|---|---|
> | 计划 A | T1–T4（阶段 1） | ✅ 中文可听性改善，模型不变 |
> | 计划 B | T5（阶段 2a） | ✅ 音色质量跃升 |
> | 计划 C | T6–T7（阶段 2b + 收尾） | ✅ 前端保真度 |
>
> T6 **是否启动由 V27 决定**（§4.4），所以计划 C 的范围要到那时才确定。

### T1 — 验证点（先做，阻塞后面）

- **V23**：offscreen 文档里跑 `jieba-wasm`（仿 P4 T1 的探针方式）：能否进包、
  初始化耗时、`cut(text, true)` 的首次调用开销。
- 产出：结论回写本节；若 V23 不成立，阶段 1 的方案要改（§5 退路）。

### T2 — 阶段 1 的格式对齐（#1–#3）

- `lib/models/phonemize/chinese.ts`：删 U+032F、jieba 词边界、标点拼接。
  **不动 `toneSandhi`**（§1.2 C）。
- 接入 `jieba-wasm`（**必须先做 V23**），`cut(text, true)` —— `hmm` 不能省（§3.2）。
- `scripts/compare-legacy-g2p.py`（对齐证据）。
- 更新既有单测断言 + 新增格式断言。

### T3 — 阶段 1 的补丁表（#4）

- `lib/models/phonemize/patches.json` + 匹配逻辑（最长匹配、按位置覆盖）。
- §1.3 全部错例 + 姓氏模式 + 「的/地/得」。
- 「每条补丁都生效」的不变量测试。
- **验收指标**：试听页已经证明「对齐 A+B+D + 补丁」与 `legacy 参考` 在 s3 上
  **ids 逐位相同**。T3 完成后，`scripts/compare-legacy-g2p.py` 应该能对
  三句话都报出这个结果（除 §3.6 的例外）。

### T4 — 阶段 1 验收

- **V24**：用户试听。产出结论回写 §5（验证点表）。
- 若听感变差 → 按 §3.7 回滚顺序处理，重新验收。

> **试听工具本身也要验收（已发生一次教训）**：第一次试听时 `legacy 参考` 那个
> 对照 clip 是错的 —— 它漏了 `map_punctuation`，全角标点被 normalizer 静默剥掉，
> clip 里**没有任何停顿**，根本不是训练目标。一个「对照样本」错了比没有对照更坏，
> 因为它会让人得出相反的结论。
>
> 所以 T4 的第一步不是听，而是**先把对照样本钉死**：`legacy 参考` 必须由
> `misaki` 的 legacy 路径逐字符产生，并过 §4.2.1 的字符集断言；
> 同时「现状」变体必须与产品代码的输出**逐字符相同**（试听页的
> `gen-variants.mjs` 已经这么做，产品实现时要保持）。

### T5 — 阶段 2a：换模型 + 换 tokenizer

- 注册表加 v1.1-zh（**fp32 单档**）、100 个音色表、新 `音节 → 注音符号` 生成脚本与产物。
- 输出格式：注音符号 + 数字声调 + `/` 分隔 + **重新打开变调**。
- **V26**（offscreen 真机）+ **V27**（用户试听）。

### T6 — 阶段 2b：移植 `ZHFrontend`（**按 V27 的结论决定是否启动**）

- `ToneSandhi` 规则 + 儿化 + `jieba-wasm` 词性（V25）+ `large_pinyin` 差异表（V25）。
- 与 Python 版 `ZHFrontend` 的对照脚本。

### T7 — 收尾

- 删除 `poc/kokoro-v11zh-webgpu/`（一次性 spike，结论已进本 spec）。
- 更新 `docs/superpowers/plans/2026-09-30-p4-on-device-models-spec.md` 的
  §3.11（中文管线）与 §6（验证点）——**P4 的 §3.11.2 描述的管线在 P5 之后不再准确**。
- 若 v1.1-zh 落地，P4 的 §3.7 档位表与 §1.4 体积表要重写。

## 8. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| **格式改动方向错了**（模型不是按 legacy 训练的） | 阶段 1 全部白做，听感变差 | 4 项独立可回滚；V24 试听；对照脚本量化 |
| **`jieba-wasm` 在 offscreen 不可用 / 体积不可接受** | 阶段 1 #3 与阶段 2b 的共同前置 | V23 先验；退路见 §5 |
| **`fp16` 被误用**（它最快） | 产出纯 NaN，且**错得没有声音** | 注册表不提供 fp16 档；构建产物断言「不含 fp16 模型」 |
| **`large_pinyin` 差异表过大** | 扩展包体积失控 | V25 实测；只取高频词 |
| **324MB 模型在 offscreen 里内存不足 / 被回收** | 阶段 2 不可用 | V26 先验；保活或降级 wasm |
| **阶段 2a 听感不达预期** | 2b 成为关键路径，工期延长 | §4.4 已把它设计成决策点（V27），不是意外 |
| **`pypinyin` 与 `pinyin-pro` 都不对**（§1.4） | 个别词仍然错 | 补丁表是唯一出路；v2 的差异表生成 + 人工抽检 |
| **原始文本被直接喂给 tokenizer**（§4.2.1） | 静默产出错音，**不报错** | 「音素串不含汉字」的单测；不用 `pipeline('text-to-speech')` 那条路 |
