3. **P5 §1.5 明确写着 v1.0 音色不该加变调与儿化**——生产用的就是 v1.0。这条不是

## 一、放在管线哪里，数据长什么样

```text
数字 → 标点 → 分行 → jieba 分词(+词性) → pinyin-pro 读音 → **变调 → 儿化** → 音节表 → 闸门
```

新模块 `crates/phonemize/src/backends/tone_sandhi/`：

| 文件 | 内容 |
|---|---|
| `mod.rs` | 规则：`pre_merge_for_modify` 的六步合并、`modified_tone` 的四组规则、`_merge_erhua` |
| `tables.rs` | 四个词表，按字节序排好，用 `binary_search` 查 |
| `NOTICE` / `LICENSE-Apache-2.0` | 署名与许可 |

**「后处理」的字面意思是：它只改声调，不改音节。** 输入是每字一个读音
（`pinyin-pro` 的 `ni3`），输出是每个还活着的字一个音节串，格式是
`syllable_to_ipa` 认识的那种：`ni2`，以及带儿化韵尾的 `wanr2`。
一个字的声母韵母是哪几个音素由 G2P 决定，这一层不碰。

```rust
pub struct Plan {
    /// 每个还活着的字一个音节，按顺序。儿化吃掉的「儿」没有自己的条目。
    pub syllables: Vec<String>,
    /// 每个词几个音节（jieba 的词，经过合并之后），和 `syllables.len()` 对得上。
    pub word_lengths: Vec<usize>,
}
```

**`word_lengths` 是必须的**，而且它不是副作用：`_merge_bu` 会把孤立的「不」粘到后一个词上、
`_merge_er` 会把「儿」粘到前一个词上、`_merge_yi` 会把「一」两边粘起来。合并后的词就是
送进 tokenizer 的词，所以 `3.14`（三点一四）的 `一四` 是一个词、空格消失，`不怕` 是一个词。
这是忠实照抄的结果，代价是**间距**也变了——而间距是模型学到的东西（阶段 6 就是为了它才引入
jieba）。14 条受影响的对照句里有 1 条是这个原因（`3.14`）。见 §七。

### 词性的来源，以及它为什么不是 HMM

`_neural_sandhi` 有三分之一的分支读词性。词性来自 **jieba 词典第三列**，
`SegmenterZh::tagged_words` 就是 `Jieba::tag`：

- **词典里有的词，两边词性一致**，因为那是同一份数据。
- **词典里没有的词是 `x`**：会猜词性的那个复合 HMM 在 `jieba-rs` 的 `default-dict` 特性后面，
  而这个特性不能进 wasm（C zstd，见 `Cargo.toml`）。后果很窄——Python jieba 给 `还书` 标 `v`，
  这里标 `x`，读词性的规则就不触发。**没有读错音；少应用一次轻声。**

`cut`（`word_lengths`，阶段 6 的接线）与 `tag`（`tagged_words`，本阶段）是同一份词典的同一次
游走。这句话是断言出来的而不是假设的：`segmenter_zh::tests::agrees_with_word_lengths` 在
47 句语料上逐句比较两个 API 的词边界。**如果它们不一致，间距会取决于变调开没开**，
而那是没有别的东西会发现的差异。

## 二、四组规则

`modified_tone` 的顺序是 `_bu_sandhi` → `_yi_sandhi` → `_neural_sandhi` → `_three_sandhi`，
**顺序是承重的**：三声规则读的是前三组留下的声调。
（`p6-paddlespeech-analysis.md` 里那个顺序是错的，这里是照代码抄的。）

| 组 | 规则 | 例 |
|---|---|---|
| 三声连读 | 两个三声，前一个变二声 | `你好` → ni2 hao3；`老李` → lao2 li3 |
| 三声连读 | 三字词先按 jieba 搜索模式切开 | `纸老虎` → 纸/老虎 → zhi3 lao2 hu3；`蒙古包` → 蒙古/包 → meng2 gu3 bao1 |
| 三声连读 | 四字词切两半，各自判断 | `甲乙丙丁` → jia2 yi3 bing3 ding1 |
| 一 | 一 + 四声（或轻声）→ 二声 | `一次` → yi2 ci4 |
| 一 | 一 + 其他 → 四声 | `一天` → yi4 tian1 |
| 一 | 一X一 → 轻声；第一 → 一声；数字串不动 | `看一看` → kan4 yi0 kan4；`第一` → di4 yi1；`一二三` → yi1 er4 san1 |
| 不 | 不 + 四声 → 二声 | `不对` → bu2 dui4 |
| 不 | V不V 的「不」→ 轻声 | `看不懂` → kan4 bu5 dong3；`对不起` → dui4 bu5 qi3 |
| 轻声 | 语气词结尾、的/地/得、了/着/过（带词性）、们/子、上/下、来/去、量词「个」 | `我们`、`桌上`、`上来`、`两个` → ge5 |
| 轻声 | 叠字（名词/动词/形容词） | `妈妈`、`说说` → shuo1 shuo5、`高高兴兴` → gao1 gao5 xing4 xing5 |
| 轻声 | 417 词的轻声词表（词本身或末两字命中） | `朋友` → peng2 you5、`眼睛` → yan3 jing5、`明白` → ming2 bai5 |
| 儿化 | 词末「儿」读 er2/er5 且不是独立音节 → 前一音节加 `r` | `玩儿` → wanr2、`门儿` → menr2、`没事儿` → mei2 shir4 |

`pre_merge_for_modify` 的六步（不 → 一 → 叠词 → 连续三声 → 边界三声 → 儿）也全部实现了，
理由在 §一：孤立的一个「不」没有后字，永远拿不到后字决定的变调。

**五字及以上的词一条三声规则都不适用**——参照实现只有二、三、四字的规则，
合并那一步也把词长卡在 3。这是照抄的，不是漏抄的，`tone_sandhi.rs` 里有一条测试钉着它。

## 三、一/不 变调：本来就在做

`pinyin-pro` 的 `special.mjs` 里有 `toneSandhiMap`（`一`→4声:yi2、1/2/3声:yi4；
`不`→4声:bu2）和 `toneSandhiIgnoreSuffix`（七对例外：一的、一是、一而、一之、一后、一也、一还）。

动手前实测：

| 输入 | pinyin-pro（阶段 6 就在跑） | 参照实现 |
|---|---|---|
| 一个 | yi2 ge4 | i2 e5 |
| 一天 | yi4 tian1 | i4 ian1 |
| 一次 | yi2 ci4 | i2 ii4 |
| 不对 | bu2 dui4 | u2 uei4 |
| 不好 | bu4 hao3 | u4 ao3 |
| 看一看 | yi0 | i5 |

**四条验收标准里三条本来就是绿的。** 本阶段真正补上的缺口只有两个：

1. **V不V 的「不」→ 轻声**（`看不懂`、`对不起`、`差不多`）——`pinyin-pro` 没有等价规则。
2. **一 + 轻声 → 二声**——`pinyin-pro` 的规则表里没有 `tone 0` 这一档。

第三条「一零零 类数字串不动」在两边结果相同（`pinyin-pro` 的数字串规则给出同一个声调），
第四条 `第一` 也相同。

## 四、怎么验证的：直接跑参照实现

PaddleSpeech 的 `ToneSandhi` 是纯 Python，只依赖 `jieba` 与 `pypinyin`，可以 import 出来直接跑
（`zh_frontend.py` 不行，它会拉 paddle）。所以验证方式是**逐句对照**，而不是读代码：

```python
# /tmp/oracle/oracle.py —— 只抄了 _get_initials_finals 与 _merge_erhua 两个函数
seg = MODIFIER.pre_merge_for_modify(psg.lcut(text))
for word, pos in seg:
    initials, finals = get_initials_finals(word)      # pypinyin
    finals = MODIFIER.modified_tone(word, pos, finals)
    initials, finals = merge_erhua(initials, finals, word, pos)
```

`pypinyin` 与 `pinyin-pro` 是两套词典，所以声调轨迹的比较必须能归因：oracle 同时输出**规则之前**
的读音（`base`）与**规则之后**的读音（`post`）。`base` 不同 ⇒ 差异属于词典，不属于规则。

**466 句的结果**：

| | 句数 | 含义 |
|---|---|---|
| 端到端逐字相同 | **354** | |
| 只有中间读音不同、最终音素相同 | **99** | 两边词典给了不同声调，规则把它们收敛到同一个结果 |
| 最终音素也不同 | **13** | 见下表；**全部是词典差异** |
| **规则差异** | **0** | |

那 13 句（左边是 pypinyin 的韵母，右边是 pinyin-pro 出来的音节）：

| 句 | pypinyin → 规则 | pinyin-pro → 规则 | 谁对 |
|---|---|---|---|
| 数数 | u3 u4 → 3 4 | shuo4 shuo4 → 4 4 | **pypinyin**（`数数` 是 shǔshu；pinyin-pro 的短语表把 `数数` 标成了 shuòshuò，那条数据是错的） |
| 哪个 | a3 e5 → 3 5 | na3 ge4 → 3 4 | **pypinyin**（`pinyin-pro` 有 `那个` 的短语条目、没有 `哪个` 的） |
| 老头儿 | ao3 our5 → 3 5 | lao3 tour2 → 3 2 | **pypinyin**（它的短语词典里 `老头` 的 `头` 是轻声；而且 `老头` 不在轻声词表里，规则改不动） |
| 瓜子儿 | ua1 iir5 → 1 5 | gua1 zir3 → 1 3 | **pypinyin**；`瓜子` 在 `must_not_neural` 里，规则**故意**不碰它 |
| 鸡子儿 | i1 iir5 → 1 5 | ji1 zir3 → 1 3 | 同上 |
| 瓜子 / 瓜子仁儿 | ua1 ii5 | gua1 zi3 | 同上 |
| 看门儿的 | an4 enr2 e5 | **kan1** menr2 de0 | **pinyin-pro**（`看门` 是 kānmén；pypinyin 的短语词典给 kàn） |
| 唱片儿 | ang4 ianr1 → 4 1 | chang4 pianr4 → 4 4 | **pinyin-pro**（唱片是 chàngpiàn；pypinyin 给 piān） |
| 挨骂儿 | ai2 ar4 → 2 4 | ai1 mar4 → 1 4 | **pypinyin**（挨骂是 áimà） |
| 纸卷儿 / 行李卷儿 | iii2 vanr3 | zhi3 juanr4 | **pypinyin**（纸卷儿是 zhǐjuǎnr；pinyin-pro 给 juàn） |
| 正儿八经 | eng4 **er2** a1 ing1 | zheng4 **er0** ba1 jing1 | **都不对**（儿是 ér；pinyin-pro 给轻声、pypinyin 给二声——两边都不影响规则） |

外加一条**分词差异**：`psg.lcut` 与 `jieba.lcut` 不是一个东西——
Python jieba 的 `posseg` 把 `人设曾经` 切成 `人|设|曾经`、`我们中出了一个叛徒` 切成
`我们|中|出|了|一个|叛徒`，而 `jieba.lcut` 与 `jieba-rs` 给的是 `人设|曾经`、`我们|中出|了|…`。
**这一点上偏离参照实现是对的**：训练目标（misaki legacy）用的是 `jieba.lcut`，
阶段 6 的语料也是按它钉的。

这 13 条**都不是规则的问题**，所以没有任何一条值得去「修」——修的地方是
`pinyin-pro` 的短语表（P5 §3.3 的补丁层），不是变调层。

## 五、三处刻意偏离 PaddleSpeech

每一处都有测试钉着，理由都在这段里。

### 5.1 一的七个例外丢了

`pinyin-pro` 在 G2P 里跑同一套一/不 规则，并且带一张「不适用」的清单
（`toneSandhiIgnoreSuffix`：一的、一是、一而、一之、一后、一也、一还）。
本实现照 `_yi_sandhi` 的字面实现，于是**从后字的声调重新推导**，那七个例外就没了：
`一是` 出 *yí shì*，而 G2P 说的是 *yī shì*。

两种读法都有出处（这张例外清单对应的是「一是…二是…」这种并列、重读的「一」），
差别是一个声调箭头。选「照抄」而不是「让 G2P 赢」的理由是：一个规则层偷偷对七个词
不生效，比一个规则层和 G2P 有两套答案更难查。如果日后要改回去，判据是
`pinyin-pro` 的 `special.ignored`，`tone_sandhi` 只需要多一个入参。
测试：`a_sandhi_the_g2p_declined_is_still_applied`。

### 5.2 儿化音保留韵尾（这一条是**照抄**，任务书才是错的）

任务书写「`an` + 儿 → `ar`（"玩儿" wan2 er2 → war2）」。PaddleSpeech 的代码是：

```python
new_finals[-1] = new_finals[-1][:-1] + "r" + new_finals[-1][-1]
```

即**韵母原样保留 + r + 原来的声调**。`玩儿` 的韵母是 `uan`，所以是 `uanr2`，
音节 `wanr2`（*wánr*），不是 `war2`。任务书那个形状是音系学的**描述**
（[waɻ]，鼻音并入鼻化元音），不是参照实现的行为。丢韵尾才是自创规则，所以没丢。
测试：`the_erhua_coda_keeps_the_final_it_joins`。

### 5.3 `银行行长` 的叠字不算叠词

`_neural_sandhi` 的叠字规则是「相邻两字相同且词性以 n/v/a 开头 → 后一字轻声」。
`银行行长` 被 Python jieba 当成**一个词**，于是银行 的「行」后面跟着 行长 的「行」，
规则触发，参照实现把它读成 *yín háng **hang** zhǎng*。**这个词就在本项目的语料里。**

本实现多问一句：这一对相同字不能跨 `_split_word` 找出来的子词边界。
真正的叠词不跨——`妈妈` 是一个子词、`高高兴兴` 是 `高高`/`兴兴` 两半，
而 `银行/行长` 的重复落在接缝上。两个字词的例外不是特例：jieba 搜索模式把 `说说`
切成 `说`/`说`，接缝**就是**那对重复。
测试：`a_repeat_across_a_sub_word_boundary_is_not_a_reduplication`。

## 六、儿化音的真实形状

**没有 13 条规则。** 分三层说清：

1. **PaddleSpeech 的 `_merge_erhua`** 是一条通用规则（上面 5.2 那行代码），
   外加三张判据：`must_erhua`（8 词，必须儿化）、`not_erhua`（48 词，绝不儿化）、
   `pos in {a, j, nr}`（形容词/简称/人名不儿化），以及「词末是儿且读 er2/er5」。
2. **完整的韵母变换表**在 `generate_lexicon.py` 里，它生成的是
   声母(22) × 韵母(39) × 儿化标记(2) × 声调(5) 的笛卡尔积，再按拼音正字法过滤。
   这不是「13 条规则」，是一张**穷举表**——因为参照实现的音节表就是按这张表建的。
   我们没有这张表：音素由 `pinyin-table.json` 决定，而那张表来自 misaki，
   里面**没有**任何儿化音节。
3. 所以本实现的形状是：**音节上加一个 `r`，由 `pinyin.rs::split_erhua_coda`
   剥下来、把 `ɻ` 追加到 IPA 上**。`wanr2` → `wa0n` → `wa↗n` → `wa↗nɻ`。
   没有新增音节表条目，也没有给表里塞一个「从未有模型见过」的音节。

**v1.1-zh 不是这个形状。** misaki 的 `zh_frontend.py` 用 `final + "R" + tone`，
因为 v1.1-zh 的 vocab 里有 `R` 而没有 `ɻ`（实测：`ɻ`/`ɚ`/`↗` 只在本阶段用到的 v1.0 vocab 里，
`R`/`1`/`5` 只在 v1.1-zh 里）。等注音前端真的落地时，分岔点就是
`split_erhua_coda` 这一个函数。现在 v1.1-zh 走 IPA 路径本来也过不了闸门（`ɚ`、`↻` 不在它的 vocab 里），
所以这不是新增的失败类别。

## 七、对照测试改了什么

`tests/zh_pipeline.rs` 的语料是**JavaScript 前端**的输出（47 句，生成器在阶段 8 已删）。
JS 前端不做变调、不做儿化，所以：

- 语料仍然逐字对齐，但**通过 `ToneRules::Off`**——`legacy()` 直接驱动
  `pipeline::phonemize_zh(.., ToneRules::Off)`，因为 `Phonemizer` 出货的是 `On` 且不接选项。
- **出货管线也对着同一份语料断言**，在
  `the_tone_rules_change_exactly_these_samples` 里：表里 14 句必须**不同**且等于新值，
  表外 33 句必须**相同**。两个方向都断言，所以「变调是唯一的差异」是被证明的而不是被希望的，
  而且将来哪一个阶段因为别的原因改动了输出，会在那里红，而不是悄悄把语料改掉。

**14 句的变化**（左边 JS，右边出货）：

| 句 | JS → 出货 | 原因 |
|---|---|---|
| 你好世界 | ni↓xau↓ → **ni↗xau↓** | 三声连读 |
| 你好世界123 | 同上 | 同上 |
| 你好，世界。 / 你好 世界 / 你好   世界 / 你好　世界 / `  你好世界  ` / 你好あ世界 | ni↓ → **ni↗** | 同上（标点、四种空白、kana 各一条，验证分段不影响变调） |
| 我有3只猫 | wo↓ jou↓ → **wo↗jou↓** | 我+有 合并成词，三声连读 |
| 我们中出了一个叛徒 | i↗kɤ↘ → **i↗kɤ** | 一个 → 个 轻声 |
| 他是一个非常努力的学生… | i↗kɤ↘ → **i↗kɤ** | 同上 |

| 3.14 | `i→ sɹ̩↘` → **`i→sɹ̩↘`** | 合并：一四 是一个词，**空格消失** |
| 这段话的长度超过了… | 个→轻声、所以→suo↗、处理→chu↗、不做 合并 | 三声连读 + 轻声 + 合并 |

## 八、⚠️ 与 P5 §1.5 的冲突（这一节最该读）

`2026-10-01-p5-chinese-g2p-v11zh-spec.md` §1.5 的原文：

> 实测我们**完全不做**三声连读变调（18/18 缺：`你好`→`ni3 hao3`）和儿化（13/13 缺：`花儿`→`hua1 er2`）。
> 看起来很该修，**但方向是错的**：
> - 我们用的是 **v1.0 的 IPA tokenizer**…
> - v1.0 的 8 个中文音色在官方 `VOICES.md` 里评级 **D**，训练时用的 G2P 就是 misaki 的
>   **legacy 路径**——**那条路径本身不做变调、不做儿化**。
> - 模型学到的映射是「**原调音素序列 → 实际变调的音频**」。我们加变调/儿化等于**偏离训练分布**。
>
> **只有 v1.1-zh 才需要它们**（它的 `ZHFrontend` 就做变调与儿化）。

**生产用的是 v1.0。** 所以按这条论证，本阶段接线的效果可能是负的。反面的三条证据：

1. **§1.6 实测「声调箭头几乎不改变音高」**：同一句话把 `i→` 换成 `i↘`，每音节中位基频
   差几 Hz（333/258/293/203 vs 333/264/289/205），波形相关性 0.23（不是抖动，但也不像换了声调）。
   ⇒ **三声变调这一半的收益与风险都很小**。
2. **§1.2 C 的结论是「保留变调」**：语料实测 legacy 词典自己就不一致（一/不 两字词 294 条里
   56% 变调、44% 原调），关掉并不能对齐；所以当时决定保留 G2P 已有的变调。本阶段与那条
   决定一致（而且 §三 说明本阶段基本没改这一块）。
3. **儿化不是声调问题，是音节数问题**：`wan2 er2` → `war2` 是两个音节变一个。
   §1.6 的「几 Hz」论证保护不了这一条。**这是本阶段风险最大的部分**，
   尤其是 `花儿` 这类词——模型见过「两个音节」的输入。

**所以：** 按任务书接线（默认 `On`，`lib.rs` 里显式写出来），但
`pipeline::ToneRules::Off` 是阶段 6 管线的**逐字**复现，回滚是一行；
`tests/zh_pipeline.rs` 一直在跑 `Off`，所以回滚不会让任何测试变红。
建议用 §1.7 那个「用户自己的真实例句」的方法听一遍 A/B——尤其是儿化的句子——
再决定 v1.0 要不要留着它。**这不是「已经验证更好」，是「已实现、可回滚、收益待听感判定」。**

## 十一、没做 & 不确定

**没做**

1. **`large_pinyin` 那 41 万条短语词典**（P5 §4.3 方案 1 的差异表）。§四 那 13 条里大部分
   是它的缺失造成的，但那是 G2P 的活，不是变调层的。
2. **v1.1-zh 的注音前端**（`R`、数字声调、`/` 分隔），连同它的 `ToneRules` 语义。
   本阶段的 `Plan` 形状是 `Off` / `On`，第三档要做的时候是在 `spell` 与
   `split_erhua_coda` 上分岔。
3. **词性 HMM**（`jieba-rs` 的 `default-dict`），理由是不能编进 wasm。
4. **韵律预测**（`RhyPredictor`）——与本阶段无关，P6-FINAL 里也没列。

**不确定**

1. **§八 的听感判定没做。** 这是最大的一条：实现了、可回滚、理由列全了，但没有人听过。
2. **`_neural_sandhi` 那一张 417 词的轻声词表是套「正确普通话」的规则，
   不是 Kokoro v1.0 训练目标的一部分。** 它一次改动的是几千个常用词的末尾音节
   （`朋友`、`眼睛`、`时候`、`东西`…）。P5 §3.7 的一句先例支持这么做
   （「正确的读音才是用户要的，而且模型在别处见过轻声的『得』」），但那是**一个**词，
   这是 **417** 个。要缩水的话，最省的切法是只留规则型轻声（语气词、的/地/得、量词个、
   来/去、叠字），把词表整张停掉——词表是 `tables.rs` 里最大的一块，也是收益最难判定的一块。
3. **`_split_word` 是拿 jieba 搜索模式的子词当「词的两半」用的，而它在参照实现里是错的。**
   `不怎么样` 会给 `(2, "不怎", "怎么")`：名字说的是 1–2 字，实际半区是 2–4 字
   （`_neural_sandhi` 测名字、写半区的最后一个声调）。本实现**照抄了这个不一致**（有测试），
   因为改成一致会改变输出，而收益不明。这个不一致只在「名字命中词表而半区不命中」或反之时
   才可观测——目前只找到 `不怎么样` 一句。
4. **`Plan.syllables` 用 `String` 而不是借用**，每个音节一次分配。
   句子长度上无所谓（一条句子几十个音节），但如果日后要做流式长文本，这是要先改的地方。
5. **`spell` 对「没有声调的那个读音」的处理**（`哼` 的 `hng`）：声调按轻声规划，
   音节串原样回写，所以报错信息与阶段 6 一致。这条路径没有任何测试走到，
   是「不可能发生」的推断，不是实测。
